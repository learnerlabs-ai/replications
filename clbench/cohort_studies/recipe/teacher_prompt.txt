EXTRACTION ALGORITHM
1. Distinguish observed success, local progress, execution error, semantic mismatch, ambiguous result, changed environment and incomplete evidence. A failed task can contain valuable supported local procedures. Do not require whole-task success.
2. Identify the actual decision states encountered. Recover prerequisites and why a particular action is supported there. Include entry discovery, post-diagnostic execution and completion when evidence supports them. A correct SQL query in an already-discovered state is not a complete exploration policy.
3. Released-answer feedback: compare attempted result/procedure to released result. Separate candidate unit, population, identity, aggregation and arithmetic explanations. A scalar answer does not uniquely identify the correct procedure. Extract a verified correction only if evidence establishes it; otherwise add the discriminating observation to evidence_gaps and teach the supported diagnostic decision. Never insert a released answer into a student's earlier state and call it pre-answer knowledge. Do not perform unauthorized extra environment queries.
4. Match supported decision points to the supplied fixed catalogue. No new generator IDs. Missing support for one generator or one contrast member must not suppress independent supported decisions. Declare omissions; do not substitute easy variants for absent hard branches.
5. Generalize through explicit invariant-preserving parameterization: task, earlier actions, observations, dependent values and next response use the SAME binding. Known prerequisites -> direct action; unknown prerequisites -> appropriate inspection. When observation establishes the missing information, generate a separate next decision that uses it. Do not repeat obsolete error assumptions after repair.
6. Plan/composition: declare dependencies and intermediate effects. Compose only compatible preconditions. Produce the next action from a specific point in the composed process, not a concatenation of disconnected answers. Longer trajectories are input context; the target is ONE next response.
7. For consultant role, use the supplied consultant serving state and output schema for the next-response target. Prior trajectory actions remain actor actions under history_action_schema, NOT consultant advice. B4 wraps the actor-state trajectory into the consultant serving envelope exactly once. Advice must be relevant to the actor's current state, include immediately applicable next steps, and distinguish conditions/invalidation. Do not turn a successful code patch into generic advice divorced from the task state. Do not independently alter the actor system prompt.
8. Coherent labelled hypothetical fixtures are allowed. Synthetic failure/result observations must follow the declared transformation or fixture. They need not have occurred in the live trace. Do not falsely reject all counterfactual practice merely because it is not an exact observed history. Unsupported semantic claims remain hypotheses, not facts.
9. Existing procedure inventory is fallible compiler state. Reuse unchanged rules; revise when evidence changes them; name dependencies invalidated by the revision. Do not regenerate identical content under new IDs. A new decision state can be a valid revision even if the core rule is unchanged.
10. Return source-linked evidence gaps with {id, premise, missing_evidence, proposed_observation, task_relevance:0..1, uncertainty:0..1}. These are proposals under the tool budget, not permission for extra queries. No guaranteed supply/performance claim.

The packet trains one learner after this evidence boundary. Apply supported stable learned conventions consistently across that packet's real-environment decisions. Do not mark a premise unknown in one decision merely because it was unknown to the historical pre-training actor, while simultaneously teaching that premise as acquired knowledge in another decision. Retain diagnostic targets where the evidence is actually insufficient, the environment changed, or checking is independently useful. Distinguish historical discovery demonstrations from the efficient policy after acquisition.
A displayed result is not sufficient for completion. Its producing action must match the objective's scope, units, constraints and aggregation (or the equivalent requirements for a nonnumeric task). When an earlier action violates an already-supported convention, teach the next corrected action even if that earlier action returned a plausible scalar or a superficially successful artifact. Do not submit that artifact merely because it is the most recent result.
For supported failure/recovery opportunities, include contrasting decisions: (a) after the wrong action's observed result, correct or diagnose as justified; (b) after the corrected action's supported result, finish. Preserve the original objective and exact serving states. Cite the decisive difference in evidence_reason; do not insert a teacher explanation into the student input. Use actual observations or valid evidence-derived continuations; do not fabricate failed outcomes or manufacture category quotas. These contrasts teach the difference between task-aligned completion and a plausible but invalid intermediate result.

V3.21 — SELECTIVE VERIFIED TRANSITIONS (shared core addendum; everything above still applies)
In addition to procedures, identify the useful DECISION TRANSITIONS actually observed in this run's permitted evidence and return them at the root as "transition_candidates": [ ... ]. This list selects which supported real-state decisions are worth teaching; it does not create evidence. Each candidate:
{id: stable string; family_id: stable string naming the reusable decision family (same family for the same kind of decision in different tasks);
 kind: "discovery_application" | "error_diagnostic" | "inspection_correction" | "verified_completion";
 procedure_id: ID of a procedure in THIS output (or an unchanged prior procedure) whose decision renders the transition;
 decision_index: integer index of that procedure's decision. That decision MUST have state_source_id (an exact recorded actor state), no varying parameters, status "supported", and a path made only of recorded transitions whose observations cite observation_source_id;
 source_event_ids: every permitted event ID the candidate relies on (must include the decision's state_source_id and every observation_source_id on its path);
 requested_objective: {population, operation, scope, units} exactly as requested by the task — do not narrow, broaden or substitute;
 relevant_observation: short quote or field reference of the actor-visible observation that makes the target appropriate;
 target_action: the exact action object the decision's response emits under the output schema;
 target_recorded_outcome: "executed_success" | "executed_error" | "not_executed" | "final_answer" — what happened when the actor actually took this action in the recorded evidence, if it did;
 premise_status: {from_observation:[...], acquired:[...], unresolved:[...]};
 advancement_reason: one or two sentences: why this action advances or completes the requested objective in that exact state (evidence-backed, no hidden chain-of-thought);
 evidence_alignment: "supported" | "unsupported", with alignment_note.}
Rules: prefer actual observation/action transitions (discovery→application; error→diagnostic inspection; inspection→corrected action; objective-aligned verified result→completion). These are possible transitions, not a template — missing links stay missing; never fabricate success or filler chains. A whole-task success supports its final answer, not every earlier action; never propose a failed call, a redundant loop or an unsupported intermediate assertion as a target (an erroneous action may appear in the state as context for a corrective target). A successful tool call alone does not answer the question. A verified_completion target must already be supported by actor-visible observations at that state; never insert the released answer into an earlier state. Unknown premises stay conditional: a candidate with unresolved premises cannot be verified_completion and cannot target a final answer. A failed task may still supply verified discovery or diagnostic transitions. Mark evidence_alignment "unsupported" when unsure; Python rejects unsupported candidates and keeps your reasons. Return [] when nothing qualifies.
Training is SINGLE-PASS: every admitted example is presented exactly once and nothing is repeated to fill dose. Breadth therefore matters: propose every DISTINCT evidence-backed decision state that qualifies (each distinct recorded state where a correct next action is supported), meaningful parameter bindings, and validated contrasts (an erroneous or misleading earlier action shown as state context with the supported corrective target), not only one example per family. Never pad with cosmetic paraphrases, duplicated states, invented outcomes or unsupported targets; a shortfall is reported, not filled.
